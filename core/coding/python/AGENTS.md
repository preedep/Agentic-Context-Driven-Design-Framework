# AGENTS.md — Python Developer Coding

## Purpose

Guide AI-assisted development of Python backend services. Provides coding standards, architectural patterns, and conventions that AI must follow when writing new code or modifying existing code.

---

## When to Use

Use this agent when you need to:
- Write new FastAPI / Django route handlers, services, or repositories
- Add a new endpoint to an existing router
- Refactor existing code to match project architecture
- Generate boilerplate (Pydantic models, validators, schemas) for a new feature

## Coding Standards

### Naming
- Modules / packages: `snake_case` — `payment_service.py`, `payment_repository.py`
- Classes: `PascalCase` — `CreatePaymentRequest`, `PaymentService`
- Functions / variables: `snake_case` — `validate_amount`, `build_response`
- Constants: `UPPER_SNAKE_CASE` — `MAX_RETRY_COUNT`
- Test files: `test_<module>.py`

### Pydantic Models
- Use Pydantic v2 `BaseModel` for all request and response schemas
- Never expose ORM models directly in API responses — always map to schemas
- Use `model_config = ConfigDict(from_attributes=True)` for ORM mapping
- Validate all inputs at the schema level — no manual `if` checks in routers

### HTTP Layer (Router)
- Routers must be thin: parse request → call service → return response
- No business logic in routers
- Declare dependencies via FastAPI `Depends()` — never instantiate services inline
- Always use typed response models in route decorators

### Service Layer
- One file per feature domain: `payment_service.py`
- Accept and return Pydantic schemas or domain dataclasses — not ORM models
- Raise typed exceptions (`ValueError`, custom `AppError`) — not HTTP exceptions
- HTTP exception translation happens in the router, not the service

### Repository Layer
- One file per aggregate: `payment_repository.py`
- Use SQLAlchemy Core with parameterized queries — no f-string SQL
- Raise `NotFoundError` (custom) when a row is not found
- Never import router or service modules from the repository layer

### Logging
- Use the structured logger from `core/logger.py` — never `print()` or bare `logging.basicConfig()`
- Required fields on every log entry: `event_date_time`, `log_type`, `level`
- Use `structlog` or `python-json-logger` for JSON output

### Testing
- Use `pytest` with `pytest-asyncio` for async tests
- Use `httpx.AsyncClient` + `pytest` fixtures for integration tests
- Mock external dependencies with `unittest.mock.AsyncMock` or `pytest-mock`
- Repository integration tests use a real test database — not mocked sessions

## DO NOT

- Do not use `print()` for logging — use the structured logger
- Do not put business logic in route handlers — delegate to service layer
- Do not use raw SQL string formatting — always use parameterized queries
- Do not expose ORM models directly in API responses — always map to Pydantic schemas
- Do not raise `HTTPException` inside the service layer — raise domain exceptions
- Do not use mutable default arguments in function signatures
- Do not hardcode environment URLs or credentials — use `pydantic-settings` / environment variables
- Do not create new error codes without updating the project error code registry
